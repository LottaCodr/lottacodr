## About

I build products end to end — from the database schema to the last pixel of motion.

Most of my work sits where **TypeScript full-stack**, **mobile**, and **AI systems** overlap: Next.js front ends that feel alive, Express and FastAPI back ends built to survive real traffic, and payment flows people trust with their money. I care about the unglamorous parts too — queues, sockets, rate limits, validation, structured logging, and observability — because that's what separates a demo from a product.

Four years and 100+ repositories in, the loop hasn't changed: **ship it, instrument it, then make it fast.**

<br />

## Currently

- 🔭 **Building** — [Glimms](https://github.com/LottaCodr/glimms-api), an AI-native platform spanning a real-time Express API, a Python AI service mesh, and an Expo mobile client
- 🌱 **Going deeper on** — retrieval & agents: vector search with Pinecone, streaming pipelines, and evaluating AI features that have to be reliable in production
- 💼 **Comfortable owning** — the whole slice: schema, API, auth, payments, deploy, and the interface people actually touch
- 💬 **Ask me about** — Next.js, TypeScript, React Native/Expo, payments (Stripe · Flutterwave · Paystack), or shipping AI features without the hype
- ⚡ **Fun fact** — *"A superhero by birth, a supervillain by backstory."*

## How I Work

<table>
<tr>
<td width="33%" valign="top" align="center">

**Product first**

I start from the problem and the person using it — not the framework. Tech choices follow the shape of the thing being built.

</td>
<td width="33%" valign="top" align="center">

**Built to be operated**

Rate limits, circuit breakers, queues, structured logs and validation aren't nice-to-haves. They're why something survives contact with users.

</td>
<td width="33%" valign="top" align="center">

Motion, spacing and type matter. Interfaces should feel considered, and I'd rather polish it than explain it.
